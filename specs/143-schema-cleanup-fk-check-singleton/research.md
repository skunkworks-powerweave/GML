# Research 143

Five design choices documented inline below.

## (1) Why bundle three findings into one migration

Each of the three audit findings is small in isolation, and each
fix is mechanical. The temptation to ship them as three separate
migrations is real but wrong:

- **0016 (FK only), 0017 (CHECK only), 0018 (seed cleanup only)**
  would have stretched a one-day audit-closure into three
  migration files, three snapshot diffs, and three governance
  tests. The marginal value of separating them is near zero —
  they don't depend on each other, they all run quickly, they
  all affect tables in the same logical "schema cleanup" bucket.
- **One bundled 0016_schema_cleanup migration** keeps the ledger
  short and lets the snapshot diff carry both the FK and the
  CHECK in one transactional step. The seed.ts cleanup is purely
  code-level (no DDL), so it lives outside the migration entirely
  but is sequenced under the same spec id for audit traceability.

The migration's header comment documents all three findings
inline so anyone reading the SQL knows what audit closure they
are looking at.

## (2) Why `ON DELETE SET NULL` (not CASCADE) for the new FK

`observation_evidence` rows carry a `caption` (text) field that a
mentor types alongside the video upload. The caption has audit
value even after the underlying video is purged — it tells the
historical reader "the mentor noted this moment in the lesson".

- **CASCADE** would delete the evidence row when the video is
  deleted. Loss of audit data.
- **RESTRICT** would prevent the video deletion until the
  evidence row is manually cleaned up. Too sharp — videos are
  deleted as part of the SM-3 retention policy (spec 011) and the
  policy shouldn't be blocked by orphan-evidence cleanup.
- **SET NULL** (chosen) — the evidence row stays, but its
  `video_submission_id` becomes NULL. The cycle-detail page's
  join switches from "video block" to a "video removed" sentinel,
  which is the documented behaviour for purged videos elsewhere
  in the app (e.g. the SM-3 trigger in spec 042).

This mirrors how `observation_cycles.observer_id` handles the
same case: when a user is deleted, the FK is set to NULL and the
cycle persists with an "observer removed" placeholder. Symmetry
across the observation tables.

## (3) Why drizzle-kit's naming convention for the constraint

Drizzle's auto-generated FK constraint name format is
`{table}_{column}_{ref_table}_{ref_column}_fk`. The migration
could have used a shorter custom name (e.g.
`observation_evidence_video_submission_id_fk`) — Postgres doesn't
care, the FK is the FK regardless of the constraint name.

But: drizzle-kit's `generate` compares snapshot FK names byte-
for-byte against what it would output for the current schema. A
custom name in the snapshot wouldn't match drizzle's auto-rendered
name, and every subsequent `pnpm db:generate` run would emit a
spurious "rename constraint" migration. Adopting drizzle's
convention up-front eliminates that perpetual diff.

This is the same reason 0009_schema_additions and 0012_videos_
pipeline_schema use the long-form constraint names — those were
auto-generated by drizzle-kit, so they naturally used drizzle's
convention.

## (4) Why we remove `bootstrapSystemSettings` (not gate it)

The original audit finding raised the race between migration
0015's INSERT and seed.ts's UPSERT. Two valid responses:

- **(A) Gate the seed-side helper** with an environment variable
  or a CLI flag so it only runs in explicit "re-seed defaults"
  scenarios. Keeps the helper available for the dev hook the
  spec-124 plan.md anticipated.
- **(B) Remove the seed-side helper entirely** and document
  `pnpm db:migrate` as the recovery hook for an accidentally
  truncated table.

We chose (B). Reasons:

1. **Single source of truth.** Two paths claiming ownership of
   the same well-known row is exactly the smell that the audit
   flagged. (A) keeps both paths alive; (B) collapses them.
2. **Migration 0015 is already idempotent.** Its INSERT has `ON
   CONFLICT DO NOTHING`. Running `pnpm db:migrate` against a
   table where the row already exists is a no-op — the migration
   runner just sees that the migration has already been applied
   and doesn't re-execute. To force re-application after a dev
   truncates the table, the recovery path is "delete the row from
   drizzle's `__drizzle_migrations` ledger, then re-run migrate".
   In practice no developer needs this — they re-seed the table
   from a snapshot or just re-create the dev DB.
3. **The race window was narrow but real.** docker-compose `up
   -d` starts containers in parallel, and the API container's
   entrypoint was previously `pnpm db:migrate && pnpm db:seed`.
   With the seed-side helper removed, the seed.ts main() no
   longer touches `system_settings` at all — the race window
   collapses to zero.

Spec 124's documented "dev hook for re-seeding defaults" use case
becomes: drop the row, re-run migrate. Spec 143's research note
formalises this contract.

## (5) The pre-existing 0017 WHERE-clause text difference

`packages/db/src/migrations/0017_whatsapp_dedup.sql:18` ends with
`WHERE "whatsapp_message_id" IS NOT NULL` (column reference
unqualified). When drizzle-kit re-renders the same partial-index
declaration from `packages/db/src/schema/videos.ts:104-105`, it
produces `WHERE "video_submissions"."whatsapp_message_id" IS NOT
NULL` (fully-qualified). The two strings are semantically
identical — Postgres treats them as the same predicate — but
drizzle-kit's snapshot comparator does a literal string match
and emits a spurious "drop and re-create index" diff on every
`pnpm db:generate` run.

This is a pre-existing 0017 issue, not introduced by spec 143.
The fix is to either (a) update the 0017 migration's WHERE
clause to use the qualified form (and update the 0017 snapshot
to match), or (b) update the drizzle-kit version we're pinned to
so it doesn't qualify the column name. Either fix belongs in a
follow-up spec — the migration ledger principle is "never edit
a shipped migration", so (a) would require a 0018 fixup
migration to rename the index, which is more churn than the
audit-closure run can afford.

Spec 143 deliberately leaves the 0017 diff alone. The trade-off
is documented here so a future contributor doesn't think they
need to fix it as part of spec 143's scope.

## Why the seed-side helper deletion is "code-only, no DDL"

The migration's job is to mutate the schema or migrate data. The
seed-side helper deletion is a pure source-code refactor — it
removes a function definition and its single call site from a
TypeScript file. There's no schema change, no data change.
Bundling it into the 0016 migration SQL would have been
semantically wrong (migrations are for SQL, not TS). So the
seed.ts edit lives outside the migration and is tracked as an
EDITED file in plan.md, with the rationale documented in the
seed.ts header comment for future contributors.
